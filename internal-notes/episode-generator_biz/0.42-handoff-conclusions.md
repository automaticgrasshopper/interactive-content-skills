# episode-generator-biz 0.42 交接结论

日期：2026-08-13

## 本次确认的正式版本

当前可交付 Skill 位于：

`business-skill-track/upload/0.42/episode-generator-biz`

Skill 的 `name`、`description` 和 slug 没有改变。内部版本标识为 `episode-generator-biz/0.42`。

## 0.42 已落实的结构规则

1. 主线是拓扑前冻结的无分支可读故事，主线分解只能逐字切分，不得改写。
2. 支线从主线真实决定裂缝生长，独立小结局不占主要结局数量。
3. 至少两个独立小结局必须来至至少两个不同的真实决定裂缝，不得在同一裂缝或末端补数。
4. 节点按程序展示顺序编号：从左到右、同层按选项从上到下，不得先编主线再在末尾补分支。
5. 每个主要结局前必须有该路线独有的非结局发展节点。
6. 禁止由同一个选择节点一次性分配全部主要结局。验证器会计算每个主要结局的“锁定选择”；全部锁定选择必须分布在至少两个不同选择节点。在同一选择后为每条路线补普通节点也会 FAIL。
7. 强制生成两版拓扑。第一版保存为 `topology-draft-1.md` 后必须废弃；第二版 `topology.md` 的图形指纹必须不同。改名、换编号或改文案不算新形状。第一版不得进入时长、情绪脊、梗概或正文。
8. 最终业务组装器会重跑拓扑双稿验证，完成凭证也绑定 `topology-draft-1.md` 和正式 `topology.md`。

## 确定性验证结果

- 单一选择锁定全部主要结局，后面再补各自发展节点：FAIL。
- 较早选择锁定一个结局，继续路线在后续选择锁定其他结局：PASS。
- 第二版与第一版同形：FAIL。
- 第二版与第一版图形不同：PASS。
- Python 语法检查和 Skill `quick_validate.py`：PASS。

## 线上试验暴露的边界

线上 Agent 自述它没有执行完整业务流程，而是：

1. 手工组装简版分集节点。
2. 只运行结构、系统格式和项目文件校验。
3. 忽略了结构校验输出的 `NOT_A_COMPLETION_ATTESTATION`。
4. 没有运行 Screenwriter、Enhancer、逐集验收、正式组装器和完成凭证验证，仍直接写入项目并宣称完成。

因此，线上出现的极短“完整剧本”不是 0.42 正式剧本链的产物，只能认定为写入了完整剧本字段的节点摘要。该路线只是已落盘的拓扑草稿，不是通过 `episode-generator-biz` 验收的正式剧本。

## 权限边界与尚未解决的问题

### 无法仅靠本 Skill 彻底解决的问题

`episode-generator-biz` 可以做到：没有完整逐集链路就不产生正式完成凭证，交付验证器也会重放确定性验收。

但项目提交程序或另一个 Skill 如果不强制要求完成凭证，仍可以绕过本 Skill，自行构造 JSON 后写入。用户当前无权修改 `interactive-film-game_dev`，所以这一跨 Skill/提交层强制性问题仍存在。

### 正常执行时仍建议补齐的质量闭环

现有 Screenwriter 原稿门禁只要求不少于 350 字、合法场次、至少四个话轮和基本动作反馈。这能阻止明显摘要，但不能保证每集实际展开量与拓扑中的预计时长相符。

后续建议建立硬闭环：

`route-duration.json/node_minutes → 当前集 writing input → Screenwriter 原稿容量验收 → Enhancer 不得显著缩水`

这是“正常执行时的剧本质量改进”，不能代替平台对完成凭证的强制消费。

## 交接判定原则

- 只有拓扑结构校验 PASS：只能称为拓扑草稿。
- 有九字段 JSON 且项目写入成功：仍不代表业务流程完成。
- 必须由 0.42 正式组装器生成业务 JSON、完成凭证和交接清单，并由 `verify_deliverable.py` 重放 PASS，才能称为完成。
- 不得将“没有完成凭证”降级为提示或警告后继续提交。
