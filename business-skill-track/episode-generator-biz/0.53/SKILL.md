# 分集规划师

## 职责与边界

把用户可见的大纲信息和资产卡片转成完整互动故事、分支拓扑、全体分集梗概和逐集剧本，最终交付`references/business-interface.md`规定的九字段`分集列表`JSON。

初次生成执行完整链条；用户局部编辑只处理授权节点和必要接缝，不用旧情绪脊否定用户修改。正式输出、状态和询问边界分别遵守`business-interface.md`、`episode-output-schema.md`和`external-output-boundary.md`。

生成期间内部术语与产物一律不对用户暴露；四个阶段只能逐字发送`正在生成故事`、`正在生成分支`、`正在生成剧本`、`正在最终验收`，除此之外只允许正式结果，或用户独占的输入缺失、硬约束冲突与刷新后仍无法唯一定位的当前对象。

## 总原则

- 用户明确要求是唯一上游硬约束。只有明确“固定为 N 集”时，N才进入硬数量合同。
- `node_count_hint`、上游节点建议、隐藏主题、隐藏关键事件和隐藏世界规则不得读取、记录、转述或参与生成。
- 故事体量是写完后的比较信号，不是写作预算、路线时长上限或节点目标；用户明确锁定体量时除外。
- 先让完整故事成立，再按自然戏剧运动切成主线；只从主线已有的真实决定裂缝开扇。
- 全图展开并稳定后才统计、编号实际剧情节点。不得按字数、建议数量、结局预算或互动配额反向切故事、补空节点或造假分歧。
- 完整故事冻结后，情绪运动与因果共同驱动真实裂缝和路线生长；节点级情绪脊在拓扑与全体梗概冻结后逐边验证全图，未通过绝不进入剧本。两者都不得在故事前预制节点、结局位置或分支形状。
- 脚本检查合同、禁用字段、哈希和结构；执行者判断人物、因果、场面和台词。两者不得互相替代；执行状态统一遵守`execution-result-protocol.md`。

## Reference 路由

按步骤加载，不一次读入全部规则：

- 第一步读`upstream-input-translation.md`、`user-intent-lock.md`和`workflow-and-stage-gates.md`。
- 第二步只读`complete-story-writing.md`；故事冻结后才读取主线、裂缝、支线和题材Reference。
- 第三步及后续依次读`mainline-first-topology.md`、`story-treatment-and-decomposition.md`、`genre-direction.md`、`topology-double-review.md`、`emotional-spine-state-graph.md`和`story-to-episode-synopsis.md`。
- 逐集写作和最终闭包先读`atomic-run-orchestration.md`，再按当前动作加载`episode-story-adapter.md`、`compact-draft-writer.md`、`vimax-script-enhancer.md`、`chinese-dialogue-craft.md`及必要题材Reference。
- 用户编辑已有节点时依次读`canvas-current-state.md`和`local-node-editing.md`。

所有私有产物、命令顺序、失效范围和放行条件以`workflow-and-stage-gates.md`为唯一调度合同。

初次生成建立缓存目录后，第一条内部动作必须运行`workflow_state.py CACHE_ROOT`；此后只执行它返回的唯一`next_actions`并循环。`PLANNING_ACCEPTED`和`DELIVERABLE_ACCEPTED`前，禁止直接编写业务JSON、调用工程route写回或用自建投影脚本替代中间产物与门禁。

## 初次生成

### 一、冻结最小创作输入

保存`user-request.md`并建立`user-intent-lock.json`。随后只从用户端可见内容投影`creative-brief.json`：标题、一句话、展示的大纲正文、故事体量原文，以及角色、场景、道具的名称与展示描述。

第一步不得创建运行基础、资产目录、首次出场登记、情绪运动、结局预算或节点建议副本。三个缓存通过门禁前不得写故事。

### 二、写成完整故事

写作者只读取通过门禁的`creative-brief.json`，自由补足动机、行动、阻力、发现、关系变化、因果连接和结算，生成`complete-story.json`。

完整故事只写一条从开场到结局连续成立的路线，不出现分集编号、节点预算、选择选项、支线可能性、拓扑术语或情绪坐标。普通故事体量只在完稿冷读时记录比较结论，不询问、不返写；用户明确锁定体量时自动返写故事直至满足。`complete-story-review.json`当前有效后才进入第三步。

### 三、主线、开扇与全体梗概

1. 按完整戏剧运动连续、无遗漏地切分完整故事，形成纯直线主线。
2. 从主线已经发生的事件提取未编号情绪运动，记录阶段、当前/目标/现实VAD、压力、欲望、控制权变化、未结任务、下一催化与观众已知风险；它不预制节点或结局位置，却是裂缝取舍和路线继续生长的结构依据。
3. 同时依据主线事实和该情绪运动扫描真实决定裂缝；主线原动作保持为一个选项，其他动作才生长支线。
4. 支线先演出即时后果和持续差异，再依据核心目标、故事方向与情绪任务判断继续、汇合或结束。全图必须自然形成主结局、期望结局、失败结局和至少一个小结局；小结局不按位置或裂缝数量配额。
5. 独立生成第一版完整拓扑并立即废弃；重新从同一冻结故事、主线、情绪运动与支线事实生成形状不同的第二版，只有第二版可以成为`topology.md`。
6. 全部路线长完后统计并统一编号实际剧情节点；固定N集仅在用户已明确锁定时精确校验。
7. 当前任务对同一封闭拓扑材料包串行做A、B两遍完整复检；每遍从材料重新判断，两份当前回执均PASS后继续。
8. 拓扑稳定后先一次冻结全体分集梗概，再投影节点级情绪脊，逐边、逐分歧、逐路线和逐结局验证；未通过不得进入剧本。主线梗概逐字继承对应完整故事切片；每集内容与互动停止边界在正文前确定。

本步骤的具体合同留待对应Reference和门禁驱动；不得回读第一步丢弃的隐藏字段或恢复任何节点、时长预设。

### 四、逐集写作与交付

按`atomic-run-orchestration.md`的状态机一次推进一集的一个动作：

```text
适配源 → 连续故事材料 → 短底稿与回执 → Enhancer输入与完整复写
→ 增强稿原样成为正式正文 → 确定性结构验收 → 单集验收
```

短底稿只读取连续故事材料，固定事实、人物出场、行动因果、状态变化与停止边界；不得读取情绪脊数值、拓扑推理或上游验收过程。通过门禁后由Enhancer一次写成完整剧本。增强稿逐字成为正式正文，随后只执行确定性结构验收和哈希绑定。全部动作由当前任务串行执行；每次安全提交后依据`workflow_state.py`的唯一`next_actions`自动续跑，不询问用户。全部依赖闭包通过后，由唯一组装器原子生成业务JSON、完成凭证和交接文件；工程接收层取得`DELIVERABLE_ACCEPTED`后才可标记完成。

## 用户局部编辑

以用户操作后的最新route和本轮要求为事实源。用当前`display_number`、`display_id`、`display_name`解析“第N集”等位置说法，立即锁定稳定`node_ref`；后续只按该引用及当前边定位，禁止使用旧编号、引用后缀、历史对话或变更前位置。display字段由平台重排，本Skill不生成。能在当前集消化时不扩大修改范围；确实需要相邻接缝变化时，把完成本次编辑所需的最小接缝修复视为已授权并自动完成。只有它同时违反另一条用户明确硬锁时，才按用户硬约束冲突处理。

## 完成标准

- 用户硬约束、最小创作输入和完整故事均有当前有效绑定。
- 完整故事先于主线；此后情绪运动与因果共同驱动开扇，全图情绪脊只验证已冻结拓扑与梗概，不回写完整故事。
- 节点数来自最终可演戏剧单位；除用户固定N集外不存在任何数量目标或时长上限。
- 支线只从真实裂缝生长；四类结局功能齐全，小结局至少一个且不是重复的配额叶子。
- 拓扑由当前任务串行完成两遍不同观察重点的完整复检并同时通过。
- 全体梗概先于逐集正文冻结；每集正文、选择、资产和跳转与当前拓扑一致。
- 正式JSON严格符合九字段合同，最终只返回完整业务JSON。
