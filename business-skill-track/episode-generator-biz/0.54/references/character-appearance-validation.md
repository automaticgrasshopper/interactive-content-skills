# 角色覆盖与首次出场合同

本规范只管理正式角色是否实际进入剧本、正文与`关联角色`是否一致，以及角色在每条观看路径上的首次出场是否完成必要交代。它不替代人物塑造、对白或因果复检。

## 一、正式角色索引

在私有缓存的`asset-catalog.json`中使用合同`nextplay.episode-assets.v1`：

- `characters`、`scenes`、`props`保存正式名称。
- `character_aliases`按正式角色名登记正文允许使用的简称或称呼；同一别名不得属于多个角色。
- `optional_characters`只登记本轮明确允许不进入剧本的正式角色。未列入者视为必出场角色。

不得因为正文漏写角色而事后把角色加入`optional_characters`。只有上游明确将该角色设为候选、备用或可裁撤资产时才能标记可选。

## 二、首次出场审计

在私有缓存创建`character-introductions.json`，合同固定为`nextplay.character-introductions.v1`：

```json
{
  "contract_version": "nextplay.character-introductions.v1",
  "characters": [
    {
      "name": "正式角色名",
      "introductions": [
        {
          "episode_id": "episode-001",
          "identity_evidence": "正文中的逐字短证据",
          "relationship_evidence": "正文中的逐字短证据",
          "immediate_relevance_evidence": "正文中的逐字短证据"
        }
      ]
    }
  ]
}
```

三项证据分别证明：

1. `identity_evidence`：观众能知道是谁或具有什么身份，且证据必须点明正式名或已登记别名。
2. `relationship_evidence`：观众能知道该角色与眼前人物、组织、任务或冲突的关系。
3. `immediate_relevance_evidence`：观众能知道为何此刻需要认识该角色，以及该角色正在改变什么。

证据必须是完整剧本中可逐字定位的不同短句，不得写总结、行号、字段名或“已交代”。身份证据自然承载冻结身份的核心即可，不得为了验收复制冻结句式。关系证据只证明角色怎样与眼前人物、组织、任务或冲突发生作用：称呼、命令与回应、配合、拒绝、保护、追问、任务依赖都可以。冻结人物关系用于约束人物行为和防止矛盾，不要求首次出场把每条背景关系说出，也不要求关系证据复述“前搭档”“姐弟”“拥有调度权”等关系名称。只写“守在某地”、无身份含义的当前动作、直呼名字或单独称谓，不能冒充身份或关系。

首次出场按正常戏剧语言完成。优先把身份嵌入动作，把关系嵌入称呼、反应或对白；一句自然表达可以同时让观众获得多项信息。`identity_evidence`不得以“角色名是／为／担任……”开头，`relationship_evidence`不得以旁白式“他／她／角色名是……”开头；禁止为了逐项交差连续书写人物登记。身份可写成“东闸现场负责人罗渡贴着护栏报数”或“总指挥韩嵩切进频道”，不得让已经认识的人互说“你是东闸现场负责人”或“我是全城应急总指挥”。观众从“沈乔：姐，急诊还剩五十七分钟”已经能知道姐弟与当前任务，不再让姐姐反说“弟弟”；从“总指挥韩嵩”紧接“沈砚，立即送电”已经能知道指挥关系，不再让韩嵩自述调度权；罗渡与沈砚先围绕卡锁自然配合，前搭档背景可以等真正影响行动时再揭示。本文件只在完整编剧稿已经完成后读取；若缺证据，只登记缺口并停止放行，不得向现有正文补贴角色卡原句，也不得由验收者重写角色进入段。

## 三、分支路径语义

首次出场不是按文件编号机械取最小值。验证器从唯一入口沿冻结拓扑计算：只要存在一条到达当前节点且此前从未见过该角色的真实路径，当前节点又登记该角色，该节点就是该路径上的首次出场节点。

同一角色可能因互斥分支拥有多个首次出场节点；每个节点都必须分别提供三项证据。汇合前某一路线已见、另一路线未见时，汇合节点仍可能成为未见路线的首次出场节点。

## 四、确定性门禁

运行`scripts/validate_character_appearances.py`，严格检查：

- 所有非可选正式角色至少实际出场一次。
- 每集`关联角色`只能使用正式名称。
- `关联角色`中的每个角色必须在该集完整剧本中以正式名或登记别名出现。
- 完整剧本中出现的正式名或登记别名必须回填到该集`关联角色`。
- 首次出场审计角色集合与实际出场角色集合完全一致。
- 审计节点与全路径计算结果完全一致。
- 三项证据字段齐全、互不重复、长度有效并可在对应完整剧本中逐字定位。
- 身份证据包含冻结身份核心；关系证据能让普通观众看出角色与眼前人物、组织、任务或冲突的实际联系。关系必须通过完整剧本的整段互动自然成立，不用词面匹配逼角色口述关系名称。

任一失败时只修复角色索引、对应首次出场场次或错误的关联角色字段，不顺改拓扑和无关分集。

## 五、上下文吞吐

不要把全剧正文、全部路线和全角色档案同时交给写作上下文：

1. 冻结阶段只保留正式名、别名、是否可选的紧凑索引。
2. 写当前集时只携带当前节点相关角色、直接前置知情，以及可能在本节点首次出场的角色卡。
3. 写完首次出场节点后，只截取三条逐字短证据写入审计，不复制整场正文。
4. 全角色覆盖、分支路径枚举、汇合后的“已见／未见”传播全部交给确定性脚本。

这样模型上下文随单集复杂度增长，不随全剧路径组合数量增长。
