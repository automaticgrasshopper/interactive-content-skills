# 分集规划师

## 主要职责

把游戏企划、角色描述、场景描述和道具描述转成完整互动故事、分支拓扑、全体分集梗概和逐集完整剧本，最终交付符合业务接口的九字段`分集列表`JSON。

本 Skill 同时处理已有分集结果上的单节点新增、插入、修改、重做、删除和重连。初次生成按完整四阶段流程执行；用户局部编辑只处理授权节点和必要接缝，不用原情绪脊否定用户修改。

## 输入与正式输出

执行前读取：

1. `references/business-interface.md`
2. `references/episode-output-schema.md`
3. `references/upstream-input-translation.md`
4. `references/external-output-boundary.md`

初次生成必须具备`游戏企划`、`角色描述`、`场景描述`和`道具描述`；缺少哪一项，只追问哪一项。正式输出顶层只有`分集列表`，每集严格使用以下九个一级字段，字段层级和类型以`business-interface.md`为唯一合同：

1. `分集编号`
2. `分集标题`
3. `分集剧本`
4. `剧本分析`
5. `关联角色`
6. `关联场景`
7. `关联道具`
8. `是否结局`
9. `互动节点`

情绪脊、故事、拓扑、梗概、写作材料、回执、哈希、缓存和完成凭证均为私有运行材料，不进入正式结果。对外状态和询问边界遵守`external-output-boundary.md`。

## 执行原则

- 用户明确要求是创作硬约束，优先于上游建议和默认偏好；只有安全边界、正式输出合同、客观不可实现或用户要求互相冲突时暂停确认。
- 完整故事、正式拓扑、全体梗概和逐集剧本是四层材料。上层决定内容与连接，下层只展开冻结材料，不得反向补写或改造上层。
- 初次生成先形成不带编号的情绪运动，再写完整可读故事，从故事中的真实决定裂缝生长支线；不得先按节点预算画树。
- 选择后的不同事实先分别演出，取得共同事实后才能汇合；每个选择只在来源分集的`互动节点`封装一次。
- 阶段顺序、命令顺序、输入隔离、退出码和回执都属于硬门槛。不得省略命令、手写PASS、复制旧回执、以主观检查代替脚本，或在门禁未通过时进入下游。
- 脚本检查合同、结构、证据、指纹和修改边界；执行者判断人物、因果、信息吞吐、场面和台词是否成立。脚本通过不等于语义质量通过，语义判断也不能绕过确定性门禁。
- 当前任务是唯一协调器。阶段三的状态机、原子动作、子任务隔离、失败恢复和最终闭包必须完整读取并遵守`references/atomic-run-orchestration.md`。
- 默认主动完成全部阶段。只有输入缺失、要求冲突或必须取得新的相邻修改权限时才询问用户。

## Reference 路由

按阶段加载，避免把全部规则一次塞进工作上下文：

- 冻结用户要求和运行基础：读`user-intent-lock.md`及`run-basis-and-stage-gates.md`的阶段一。
- 建立未编号情绪运动：读`emotional-spine-state-graph.md`。
- 写第一版可读故事：情绪运动通过后读`mainline-story-writing.md`；写作隔离区只读取已通过的六组故事输入。
- 分解主线、扫描裂缝、生成支线和两版拓扑：可读故事冷读通过后读`mainline-first-topology.md`、`story-treatment-and-decomposition.md`和`genre-direction.md`。
- 生成全体分集梗概：读`story-to-episode-synopsis.md`。
- 逐集适配、写作、增强、结构验收、场面复检、冷读和局部修复：读`atomic-run-orchestration.md`，并只按其中的动作读取`episode-story-adapter.md`、`vimax-screenwriter.md`、`vimax-script-enhancer.md`、`chinese-dialogue-craft.md`、`character-appearance-validation.md`、`dramatization-completion.md`、`episode-quality-review.md`和`vimax-local-repair.md`。
- 当前集出现推动剧情的书面信息时，再读`written-text-to-dialogue.md`；题材标签命中时才读`genre-direction.md`。
- 用户编辑已有节点：先读`canvas-current-state.md`完成当前全图定位，再读`local-node-editing.md`。

各阶段的文件合同、命令清单、顺序、修复边界和失效范围以`run-basis-and-stage-gates.md`为唯一总门禁合同；阶段三和阶段四的动作状态机以`atomic-run-orchestration.md`为唯一执行合同。

## 主流程

### 一、冻结运行基础

保存用户原始要求，建立用户意图合同、运行基础、资产目录和首次出场登记。四项输入、资产名称、角色运行边界和结局预算通过阶段一门禁后，生成隔离的`stage-two-input.json`。阶段二不得回读原始上游材料、用户原文或旧拓扑、旧梗概、旧正文。

### 二、完整故事、拓扑与全体梗概

严格按`run-basis-and-stage-gates.md`中的阶段二顺序执行：

1. 建立未编号情绪运动。
2. 提炼六组可读故事输入，隔离写出无分支语言的完整主线故事并冷读。
3. 按原文连续分解主线；`validate_mainline_projection.py --decomposition-only`通过后才能扫描裂缝。
4. 审计真实决定裂缝，生成支线事实、汇合、主要结局和独立小结局。
5. 先完成并丢弃第一版拓扑，再从冻结材料独立生成形状不同的正式第二版。
6. 验证路线枚举和连续映射，并对主线切片逐节点完成事件归属复检；再验证逐节点情绪脊，正式拓扑冻结后统计实际节点数。
7. 一次生成并整体验收全部梗概；主线路径梗概逐字等于可读故事对应切片。
8. 创建阶段二验收并初始化可续跑状态。

阶段二失败只返修最早失效材料及其下游。评论性判断两次局部修复后仍无确定结论时可记录告警后放行；节点不存在、路径不连续、分支跳转、结局类型、哈希或正式字段合同错误不得放行。

### 三、逐集完整写作与放行

完整读取`atomic-run-orchestration.md`，一次只推进状态机返回的当前集当前动作。每集必须形成并绑定：

```text
适配源 → 连续故事材料 → Screenwriter原稿与回执 → Enhancer输入与增强稿
→ 增强稿原样成为正式正文 → 确定性结构验收 → 场面复检与独立冷读
→ 必要时Enhancer局部修复或受控整集重写 → 单集验收
```

Enhancer增强稿或其受控局部修复稿是正式正文；复检者只出问题单，不得生成第三版正文。当前集Acceptance后才进入下一集，已验收正文退出活跃工作集。

### 四、最终验收与组装

全部分集Acceptance后，按`atomic-run-orchestration.md`执行轻量闭包：核对阶段二验收、全路径首次出场、全体单集Acceptance和运行状态，再由唯一组装器原子生成`episode-business.json`、`completion-receipt.json`和`episode-handoff.json`。

工程接收层必须自行运行`verify_deliverable.py`。只有三件套齐全、进程退出码为0且标准输出含独立一行`DELIVERABLE_ACCEPTED`时，才允许标记完成和正式投影；否则保持`正在生成中`。

## 用户局部编辑

用户在已有结果上新增、插入、删除、移动、重连或实质改写节点时，以操作后的当前图和本轮要求为事实源：

1. 先按`canvas-current-state.md`重新读取当前全部节点和边，唯一定位目标、全部直接前置和全部直接后续。
2. 再按`local-node-editing.md`把创作边界收窄为一集，只判断内容、人设和相邻接缝能否成立，不读取情绪脊或全局拓扑理由来否定用户修改。
3. 能在当前集消化时直接完成。只有关键人物生死、身份、关系、世界规则、选择去向或下一集成立条件迫使未授权相邻集变化时，才询问是否扩大修改权限。
4. 受影响正文仍执行Enhancer、结构验收、场面复检、冷读、局部修复和单集验收；未授权节点保持不变。
5. 返回当前完整九字段结果，不只返回变化片段。工程route字段、稳定节点引用、边引用和revision由调用方适配层维护，不进入本 Skill 正式输出。

内部返修和用户局部编辑不得混用：内部发现故事或拓扑错误时回到最早失效阶段；用户已明确执行的局部结构编辑不重新生成情绪脊或全局拓扑。

## 完成标准

- 阶段一、阶段二及全体单集门禁均通过，故事、拓扑、情绪脊和全体梗概已冻结并绑定。
- 每集都存在适配材料、原稿、原稿回执、Enhancer输入、增强稿、结构回执、两份复检回执和单集Acceptance；正文与最终增强稿逐字一致。
- 第一项是具有非空完整剧本的`episode-001`；分集数等于正式拓扑剧情节点数；每个有效选择只出现一次。
- 正式JSON严格符合九字段合同，并通过独立业务结构校验。
- 当前三件套通过工程接收层独立验证并取得`DELIVERABLE_ACCEPTED`。
- 最终对外只返回完整业务JSON，不包含内部过程、私有材料或工程结构。
