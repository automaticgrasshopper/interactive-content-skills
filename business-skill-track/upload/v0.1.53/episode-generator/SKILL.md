# 分集规划师

## 核心约定

- 情绪脊是唯一上层驱动：先按体量建立全篇 PAD/VAD 主干情绪脊，再从真实戏剧裂缝识别岔点。
- 分支按开扇、独立结果、带差异合流和收扇组成编织带；一个真实节点仍对应一集。
- 写作最小单元是“相邻因果拍”：触发、判断、欲望、行动、阻力、调整、即时后果、下一压力只推进相邻一步，不跳过过程直达结果。
- 选择、选择结果、路线反馈、汇合和结局分别占用真实节点。选择后的不同事实先分别演出，取得共同事实后才能汇合。
- `episode-001`本身是分支节点时，拒绝空开场或制作话术直接出选项；第一集正文播完后可以正常进入选择。
- 冻结拓扑是剧本锚。未明确解冻前，正文不得改节点、边、选项、状态条件、状态效果或结局。
- 无需用户确认，主动完成所有阶段。
- 情绪脊推导、VAD术语、内部候选、状态审计和修复记录不进入玩家可见文件。
- 最新且明确的用户要求是创作硬约束，优先于上游建议、Skill默认偏好和内部启发式；除安全边界、输出合同或客观不可实现外，不得否定、替换或删除用户指定内容。
- 用户前后明确要求无法同时成立时，必须暂停并启动 AskUser；用户回答前不得自行选择、重写或继续拓扑。

## 四项输入

完整读取：

1. `游戏企划`
2. `角色描述`
3. `场景描述`
4. `道具描述`

缺少哪一项，只追问哪一项。用户明确给出的主线、关系、规则、结局数量和结局方向优先。大纲中的`剧情节点总数建议`是可选的软区间：存在时用于拓扑体量校准，缺失时不得追问或阻塞，直接按游戏体量、情绪脊、真实分支和结局需求确定节点数。只有用户明确要求“固定为 N 集”时，精确节点数才是硬约束。

## 十一字段下游契约

每一集只输出以下十一个一级字段，顺序固定：

1. `分集编号`
2. `分集标题`
3. `分集数`
4. `选择数`
5. `分集剧本`
6. `剧本分析`
7. `关联角色`
8. `关联场景`
9. `关联道具`
10. `是否结局`
11. `互动节点`

`分集剧本`只含`单集梗概`、`完整剧本`；`剧本分析`只含`本集冲突`、`前置节点编号列表`、`后续节点编号列表`；`互动节点`只含`是否为分支节点`、`是否有选择问题`、`选择问题`、`选项列表`、`默认下一分集编号`。每个选项只含`选项编号`、`选项文字`、`目标分集编号`。

`分集数`是冻结创作拓扑中的剧集节点总数，必须为正整数；`选择数`是其中带有效互动的剧集数量，也是交付拓扑展开出的选择节点总数，必须为非负整数。二者在每一集重复同一个值。交付拓扑总节点数等于`分集数 + 选择数`。多集重复十一字段，不增加包装对象或英文键名。关联资产只能使用上游正式名称。

创作拓扑只含`episode-xxx`剧集节点：每个节点有完整剧本和一个情绪脊坐标。交付投射把每个分支剧集的互动展开为独立`choice-xxx`选择节点；选择节点只承载问题、选项和跳转，不含剧本、资产或情绪坐标，不计入`分集数`。唯一入口必须是剧集节点；分支剧集先完整播放，再进入其选择节点。

## 玩家可见画布

画布一级目录严格保留三个文件：

1. `episode-flowchart.svg`：真实节点、选择、条件、跳转、汇合和结局。
2. `episode-structure.md`：只含分集编号、标题、类型、单集梗概与玩家可见跳转。
3. `episode-script.md`：全部十一字段分集结果组成的完整剧本。

缓存、状态表、路径枚举、检查记录和中间稿全部放在画布目录之外；不得把`cache/`作为画布子目录。三个公开输出必须同目录且使用固定文件名，组装器会拒绝公开目录中的任何第四项内容。

## 阶段一：冻结故事运行基础

1. 完整读取`references/user-intent-lock.md`，先在画布外建立用户意图内部合同并运行`python3 scripts/validate_user_intent_lock.py contract <缓存目录>`。合同状态为`needs-user`时立即启动 AskUser，解决前停止后续阶段。
2. 按`references/upstream-input-translation.md`压缩四项输入；任何压缩结果不得覆盖有效用户约束。
3. 冻结故事核心、主题、题材、世界规则、体量、正式资产、必保事件和结局方向。
4. 冻结角色当下欲望、知情边界、能力边界和说话方式。
5. 只声明会被玩家行动写入、并被后续条件或结局读取的状态；可使用旗标、计数、关系、物件、证据、权限或风险，不为填表制造数值。

在画布外创建确定性运行缓存：

- `asset-catalog.json`：合同固定为`nextplay.episode-assets.v1`，分别列出本项目正式`characters`、`scenes`、`props`名称；名称必须是合法非空字符串且同类不得重名。用`character_aliases`登记正文允许使用的角色简称，只在上游明确允许不出场时才用`optional_characters`。
- `user-request.md`：本轮可见用户要求的私有源快照；只用于合同绑定，不进入公开输出。
- `user-intent-lock.json`：合同固定为`nextplay.user-intent-lock.v1`，保存有效用户硬约束、范围、冲突状态和解决记录。
- `character-introductions.json`：合同固定为`nextplay.character-introductions.v1`，按角色及全路径首次出场节点登记身份、关系、当下必要性三条正文逐字证据。
- `emotional-spine.json`：合同固定为`nextplay.emotional-spine.v1`，按分集顺序记录`episode_id`、`valence`、`arousal`、`dominance`、`turn`、`turn_reason`。
- `topology.md`：冻结节点、后继、互动类型、结局、选择问题和选项。
- `episodes/<episode-id>.md`：每集严格十一字段正文。

## 阶段二：情绪脊与分支拓扑

完整读取`references/emotional-spine-state-graph.md`：

1. 按体量确定结构引擎、节点规模、互动预算和结局数。上游节点建议若存在，必须按区间理解并尽量在区间内完成拓扑；若缺失，直接从体量、情绪脊、真实戏剧裂缝和结局需求推导，不得停止或追问。
2. 先建立全篇 PAD/VAD 主干情绪脊，不碰分支拓扑。
3. 只在幻想空间出现真实分歧且情绪轨迹发生拐点时建立选择；每个选项必须有代价、即时变化和后续差异。
4. 按开扇、独立结果、带差异合流和收扇原则，把岔点铺成宽度受控的编织带；末段结局阶梯式开扇。
5. 按规则拒绝空合流，再检查断链、死路、循环、不可达节点、无法到达结局的节点和无真实出口的选择。
6. 对规范化`emotional-spine.json`计算SHA-256，在私有`topology.md`写入不渲染的`<!-- 情绪脊校验：sha256:<64位hex> -->`机器注释；不得把哈希写成可见 Markdown 正文。每个分支剧集节点必须对应`turn=true`的情绪拐点；派生选择节点不另设情绪坐标。
7. 从企划取得预期结局总数、正式结局数和失败结局数，运行`scripts/validate_emotional_topology.py`并通过`--spine`、`--expected-endings`、`--expected-formal`、`--expected-failure`传入；不得把任一数量硬编码为固定模板。
8. 门禁通过后冻结唯一拓扑并生成流程图与结构稿，随后主动进入逐集写作。情绪脊合同、VAD范围、节点顺序、拐点理由、拓扑绑定哈希或结局数量任一不合格时，不得写正文。

## 阶段三：逐集写作

完整读取`references/causal-episode-writing.md`和`references/chinese-dialogue-craft.md`。

首次安排正式角色出场前完整读取`references/character-appearance-validation.md`。写当前集时只携带当前节点相关角色和可能首次出场者；不得把全剧正文、全角色档案或全部路径塞入单集上下文。首次出场写完即把三条短证据写入`character-introductions.json`，全路径计算交给脚本。

若当前集出现信件、短信、聊天记录、书页、日记、邮件、报告、病历、通知、名单或屏幕文字，且文字内容推动知情、行动、证据、选择或后果，则在初稿、台词复写和独立复检前完整读取`references/written-text-to-dialogue.md`；当前集没有这类文字剧情时不要读取。

沿观看路径一次写一集，只携带：当前节点、直接前置真实结果、仍有效的状态差异、人物关系与知情、相关资产、世界规则和直接后续入口。

用网文的因果清晰度写可拍摄剧本：从人物已经面对的具体事情开始，写清他看见什么、怎样理解、为什么采取行动、遇到什么阻力、怎样调整、造成什么即时事实。对白统一写成`人物：台词`，不用台词引号。场面结尾落在可见后果、位置变化、暴露信息或迫近压力上，不用主题总结收口。

完成本轮正文后，必须在组装前对本轮生成或修改的每一集执行`references/chinese-dialogue-craft.md`中的“轻量台词复写”：单独提取台词、复写并放回原位。不得以随写自检代替；未完成不得进入阶段四。

轻量台词复写完成后，不得直接人工打开 reference 自称复检。对本轮生成或修改的每一集运行`scripts/episode_quality_gate.py packet <缓存目录> <分集编号>`，完整读取脚本输出的 reference 与当前正文复检包，再逐场独立复检。临时 JSON 必须写入理解门四项复述及正文证据、七项覆盖及逐项证据、问题、正文指纹、reference 指纹、用户要求源摘要和用户意图合同摘要；其中普通话检查必须分别举证台词与非台词描述。运行同脚本的`seal`命令生成私有回执；发现问题时先定点返修，再重新生成复检包。不得手写、复制或沿用旧回执。

所有分集完成后，按`references/user-intent-lock.md`独立生成`user-intent-review.json`，再运行`scripts/episode_quality_gate.py verify <缓存目录>`。缺少当前有效回执、覆盖或证据不全、问题未清空、复检reference变化、用户要求源或合同变化、正文一字变化均必须失败；未通过不得冻结、组装或回写状态。全局Skill版本只作为来源信息，不参与回执有效性；只有正文、复检reference、用户意图合同、检查项或回执合同变化才使回执失效。

写完只检查：

1. **事实与状态正确**：来源、持有人、知情、权限、条件、效果、选择结果和后续入口成立。
2. **因果相邻**：不跳过移动、接触、阻力、失败尝试或代价，角色决定能从欲望、认知、压力、能力和成本推出。
3. **首次出现交代**：人物、装置、组织、能力和关键名词首次使用时当场说明。
4. **人话对白**：每句回应具体对象，问答有承接，复杂信息由证据、追问、质疑和反应逐层说清。

失败只修改当前集对应问题。真实结尾变化时检查直接后续，不重写无关路线。

## 正文格式

- 场次使用`【场景名称·时段·内/外】`。
- 叙述按正常段落顺写，不使用`△`、`出场：`、镜号、景别、运镜或审稿标签。
- 对白使用`人物：台词`，不使用`人物：“台词”`。
- 普通节点不设硬字数、动作段数或台词比例；仅当`episode-001`本身是分支节点时，使用两行、60个非空白字符作为防空开场底线。
- 选择必须是玩家可执行的动作，并指向冻结拓扑中的真实目标集。

## 阶段四：运行检查与投射

先运行逐集复检脚本的`verify`门禁，再检查拓扑可达、情绪脊拐点、开扇与收扇、带差异合流、所有路线事实连续、结局可达、首次出现已交代、因果不跳拍和对白可懂。随后运行：

`python3 scripts/validate_character_appearances.py <缓存目录> --asset-catalog <缓存目录>/asset-catalog.json --introductions <缓存目录>/character-introductions.json`

通过后再运行：

`python3 scripts/validate_and_assemble_scripts.py <缓存目录> <公开目录>/episode-script.md --asset-catalog <缓存目录>/asset-catalog.json --character-introductions <缓存目录>/character-introductions.json --spine <缓存目录>/emotional-spine.json --expected-endings N --expected-formal F --expected-failure X`

组装器必须再次验证全部复检回执，并强验证：

- `asset-catalog.json`合同、字符串合法性、分类内资产重名及正文正式资产名。
- 非可选正式角色覆盖、正文与`关联角色`双向一致、全路径首次出场节点及三类逐字证据。
- 十一个一级字段及全部子字段，且不得多、缺或乱序；`分集数`必须等于冻结创作拓扑的剧集节点总数，`选择数`必须等于有效分支剧集数，且均在每集一致。
- 交付拓扑必须区分剧集节点与选择节点；选择节点一入多出、不得作为入口、不含剧本或情绪脊，交付总节点数必须等于`分集数 + 选择数`。
- 选择标记、选择问题、选项编号、选项文字、选项目标和默认下一分集。
- 前置节点、后续节点、结局标记及`【场景名称·时段·内/外】`场次标题。
- 预期结局总数、正式结局数和失败结局数。
- `user-request.md`、`user-intent-lock.json`和`user-intent-review.json`必须相互绑定；所有有效硬约束逐项覆盖、证据存在、禁用字面内容未出现、冲突已由用户解决。

从同一冻结拓扑和正文确定性生成并读回`episode-script.md`、`episode-structure.md`、`episode-flowchart.svg`，三份公开文件整组事务提交。组装阶段不得重新改写剧本。

## 修改范围

- 改上游事实：重新冻结受影响运行基础与拓扑。
- 改节点、边、条件、效果或结局：解冻拓扑，并使受影响正文失效。
- 只改某集因果或对白：把修改前缓存作为`--baseline-root`，逐个用`--allowed-changed <episode-id>`授权可变分集；未授权分集一字变化都必须失败，局部修改期间`topology.md`必须逐字节不变。真实结尾改变时检查直接后续。
- 只改语言：锁定事实、行动、状态、选择与结尾，并增加`--change-scope dialogue`；已授权分集内的非台词内容发生变化也必须失败。

## 验收

- 四项输入齐全，正式资产名一致。
- 一节点一集，所有真实路径可从唯一入口到达结局。
- 主干情绪脊先于分支；每个岔点来自幻想分歧与情绪拐点。
- 选择先分后合，无假分支；汇合保留未解决差异。
- `episode-001`为分支节点时，第一集先演出实质剧情再进入选择；后续选择继续由情绪脊、拓扑和逐集质量规则覆盖。
- 每集因果相邻、首次出现已交代、对白为`人物：台词`且自然可懂。
- 每集独立复检覆盖七项、问题清空，并与最终正文 SHA-256 一致。
- 每集严格十一字段；`分集数`等于剧集节点总数，`选择数`等于选择节点总数；资产合同、角色覆盖与首次出场合同、情绪脊合同、结局数量和修改审计全部通过；画布一级严格三个公开文件。
- 用户意图合同状态为`resolved`，所有有效硬约束已由独立履约复检举证；前后意愿冲突必须有用户解决记录。
