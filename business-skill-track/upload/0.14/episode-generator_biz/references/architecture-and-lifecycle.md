# 分集规划师架构与完整生命周期

本文用于讲解、维护、评审和技术对接`episode-generator_biz`。它解释现有规则如何协作，不新增正式输入、正式输出、数据库字段或创作门禁；执行时仍以`SKILL.md`及对应阶段Reference为准。

## 1. 总体定位

本Skill位于大纲和资产之后、分镜和视频之前。它接收已经确认的游戏企划、角色、场景和道具，完成互动影游的情绪结构、剧情拓扑、逐集剧本、质量验证、业务字段组装和Nextplay路线投影。

它不是直接把大纲扩写成若干集。正确顺序是：

```text
锁定用户意图
→整理故事与资产事实
→建立主干情绪脊
→识别真实选择
→冻结剧情拓扑
→沿拓扑逐集写作
→逐集复写与独立复检
→全剧一致性验证
→生成公开文件
→组装十一字段业务JSON
→投影网页路线
→交叉验证后一次性提交
```

## 2. 分层架构

### 2.1 创作层

- 用户意图：保存用户明确要求，处理新旧要求的覆盖与冲突。
- 世界与资产：冻结规则、角色能力、知情边界和正式资产名称。
- 情绪脊：先确定全篇情绪方向与真实拐点。
- 剧情拓扑：从真实拐点生成选择、结果、汇合和结局。
- 逐集剧本：在冻结拓扑内按相邻因果拍写完整场面。

### 2.2 质量层

- 因果检查：行动必须能从认知、欲望、压力、能力和代价推出。
- 台词复写：台词需单独提取、复写并放回原位。
- 首次出场：按每条真实观看路径验证身份、关系和当下必要性。
- 资产一致性：正文名称与角色、场景、道具目录双向一致。
- 结局验证：总数、正式结局数和失败结局数与企划一致。
- 用户履约：每项有效硬约束必须能在最终拓扑或正文中找到证据。
- 修改审计：限制局部修改的可变分集和可变内容范围。

### 2.3 业务层

- 三个公开文件：流程图、结构稿和完整分集剧本。
- 十一字段`分集列表`：工程侧唯一正式业务数据。
- 互动节点：一条记录对应一集完整剧情。
- 选择信息：只在来源分集内封装一次，不增加分集对象。

### 2.4 网页适配层

- 把每个互动节点投影成一张剧情卡。
- 把每个有效选择投影成一张独立选择卡。
- 生成剧情到选择的默认边及选择到目标剧情的选择边。
- 固定入口、连续编号、实际可视节点总数和结局可达性。

## 3. 完整运行流程

### 3.1 输入预检

初次生成读取四项正式输入：

1. `游戏企划`
2. `角色描述`
3. `场景描述`
4. `道具描述`

缺少哪一项只询问哪一项。`剧情节点总数建议`是软区间：存在时优先在区间内确定互动节点数，缺失时根据体量、情绪脊、真实分支和结局需求推导，不阻塞运行。只有用户明确要求固定集数时，具体数量才是硬约束。

### 3.2 用户意图锁定

在任何压缩、情绪推导或拓扑生成前，先保存用户要求源快照并建立私有用户意图合同。合同只登记用户明确指定的主线、关系、规则、事件、选择、结局、固定数量和禁改范围，不把Skill建议伪装成用户要求。

最新且明确的用户要求优先于上游建议、默认偏好和模型判断。若新要求明确修订旧要求，以新要求为准并保存替代记录；若两项硬要求无法同时成立，状态改为`needs-user`并启动AskUser，用户回答前停止后续生成。

### 3.3 运行基础冻结

压缩四项输入，但不得覆盖有效用户约束。随后冻结：

- 故事核心、主题、题材、世界规则和体量；
- 必保事件、结局方向和正式资产；
- 角色当下欲望、知情、能力与语言边界；
- 会被玩家行动写入并被后续条件或结局读取的必要状态。

私有`asset-catalog.json`保存正式角色、场景、道具、角色别名和可选角色。它负责名称合法性、同类重名和正文资产引用的一致性。

### 3.4 情绪脊生成

先按体量选择结构引擎，再建立全篇PAD/VAD主干情绪脊。每个互动节点记录效价、唤醒、支配和是否为拐点；选择节点不另取情绪坐标。

只有当玩家面对真实的价值、关系、风险、资源或立场差异，并且不同选择会改变情绪轨迹或后续事实时，才建立选择。带选择的互动节点必须是情绪拐点。

情绪脊与拓扑使用摘要绑定。节点顺序、坐标范围、拐点理由、摘要或结局数量不合格时，不得进入正文写作。

### 3.5 分支拓扑生成

分支使用宽度受控的编织带，而不是无限扩张的树：

```text
剧情节点
→选择节点
→不同即时结果节点
→保留差异的汇合节点
→后续选择或结局
```

每个选项必须有代价、即时变化和后续差异。禁止两个选项直接指向同一后续节点形成空合流；不同结果至少分别演出一次，汇合后仍要保留关系、信息、风险、承诺或状态差异。

拓扑检查断链、循环、孤立、不可达、非结局死路、无真实出口的选择和无法到达结局的节点。通过后冻结唯一拓扑；未明确解冻前，正文不得改变节点、边、选项、条件、效果或结局。

### 3.6 逐集写作

沿真实观看路径一次写一集。当前集只携带当前节点、直接前置结果、仍有效状态、相关角色与资产、世界规则和直接后续入口，不把全剧正文和全部角色档案同时放入上下文。

正文按相邻因果拍推进：触发、判断、欲望、行动、阻力、调整、即时后果和下一压力。具体场面必须演出过程，不能从决定直接跳到结果，也不能在一集里用摘要同时解决多个重大问题。

场次使用`【场景名称·时段·内/外】`，对白使用`人物：台词`。剧本不写镜号、景别、运镜、审稿标签或“玩家现在需要选择”等制作语言。

### 3.7 首次出场和文字剧情

正式角色首次出场必须在正文中分别提供可逐字定位的身份、关系和当下必要性证据。验证按每条真实路径计算，同一角色可能在互斥路线拥有多个首次出场节点。

信件、短信、聊天记录、报告、病历、通知、名单或屏幕文字如果推动知情、行动、证据、选择或后果，则额外执行书面文字转对白规范，避免用长篇朗读替代现场戏剧。

### 3.8 台词复写与逐集复检

每一集初稿完成后，单独提取台词，执行轻量复写，再放回原位。重点检查问答承接、信息权限、身份语体、对峙攻防、口语自然度和单句信息负荷。

随后为当前集生成独立复检包，重新读取质量Reference与最终正文，逐项提供正文证据。发现问题时只定点返修当前集，再重新生成复检包和私有回执。正文、相关Reference、用户意图合同或检查项变化时，旧回执失效；全局Skill版本号本身不导致回执失效。

### 3.9 全剧验证与公开文件

所有分集完成后，验证全部复检回执、用户要求履约、拓扑可达、情绪拐点、分支开合、事实连续、首次出场、资产一致、十一字段结构和结局数量。

通过后，从同一冻结结果事务性生成：

- `episode-flowchart.svg`
- `episode-structure.md`
- `episode-script.md`

公开目录只能包含这三个固定文件。组装阶段不得重新改写剧情。

### 3.10 业务JSON与路线投影

组装器从同一冻结结果生成只含`分集列表`的业务JSON，并验证十一字段、子字段、顺序、boolean类型、编号、选择目标、前后节点、结局和资产。

业务JSON通过后，固定投影器生成`route.json`。投影器不重新创作或推导，只把业务事实转换成网页剧情卡、选择卡和边。提案与最终合并结果都必须通过业务与路线交叉验证，才能返回页面槽位。

## 4. 两类节点与两套计数

### 4.1 业务数据层

`分集列表`每项都是有完整剧情的互动节点记录：

```text
互动节点.是否为互动节点 = true
选择节点.是否为选择节点 = false
```

如果本集播完后存在选择，只在该记录的`选择节点`对象中设置`是否有选择问题=true`，并封装唯一`choice-xxx`、问题、选项和目标互动节点。选择不另生成分集对象，也不计入业务`分集数`。

### 4.2 网页路线层

网页需要独立展示选择，因此投影层从业务封装生成一张独立逻辑选择卡。设互动节点数为`E`、唯一选择数为`C`：

```text
业务分集数 = E
网页剧情卡数量 = E
网页选择卡数量 = C
网页可视节点总数 = E + C
settings.episode_count = E + C
```

两套计数不能混用。上游节点建议只约束互动节点数，不包含选择卡。

## 5. 质量验证体系

验证分为语义判断和确定性检查。

语义判断负责：设定是否过载、人物是否讲清、台词是否自然、行为是否有因果、信息是否逐层揭示。脚本不能替代这些判断。

确定性脚本负责：

- 用户意图合同状态与摘要绑定；
- 情绪脊字段、范围、顺序和拓扑摘要；
- 节点可达、死路、循环、选择目标和结局数量；
- 正文与关联资产双向一致；
- 全路径首次出场和三类逐字证据；
- 十一字段与全部子字段；
- 逐集正文与复检回执指纹；
- 修改范围、未授权分集和非台词内容；
- 业务JSON与网页路线的节点、入口、连线和数量不变量。

任何强门禁失败时，只修复对应层的问题，不在下游字段中掩盖上游缺陷。

## 6. 上下文吞吐设计

上下文按阶段和单集拆分：

- 冻结阶段只保留紧凑资产索引和用户硬约束；
- 情绪阶段只处理情绪主干与节点功能；
- 拓扑阶段不携带完整剧本；
- 单集写作只读取当前节点和直接相邻事实；
- 首次出场只保存三条短证据，不复制整场正文；
- 全路径枚举、角色覆盖、摘要和指纹交给脚本；
- 逐集复检包一次只审一集。

因此上下文规模随单集复杂度增长，不随全部分支组合爆炸。

## 7. 公开与私有边界

玩家和业务侧只接收三个公开文件、十一字段业务结果及其网页投影。用户意图合同、冲突记录、情绪脊、内部拓扑推导、资产索引、首次出场证据、复检包、回执、摘要、缓存和修复日志全部位于私有运行空间。

默认不发送过程消息。平台强制要求长任务状态且无法静默时，只发送`正在生成中`。不得把合同、情绪脊、拓扑、门禁、冷读、复检、缓存、回执或内部修复过程显示给用户。

## 8. 修改模式

- 修改上游事实：重新冻结受影响的运行基础与拓扑。
- 修改节点、边、条件、效果或结局：解冻拓扑，并使受影响正文与回执失效。
- 只改某集因果或对白：使用旧缓存作为基线，只授权指定分集；未授权分集一字变化即失败，拓扑必须逐字节不变。
- 只改语言：额外使用`dialogue`范围；授权分集中的非台词内容变化也必须失败。

创建、修改、重做和恢复都返回完整当前结果，不返回局部片段。

## 9. 失败与提交边界

生成、验证和修复期间不向页面逐个发布节点。只有原版创作门禁、公开文件组装、业务JSON校验和路线交叉校验全部通过，才允许一次性提交完整结果。

失败时不提交部分路线。重做时整组替换旧节点和边，禁止追加、合并或保留上一轮派生节点。这样可以避免第一集未落库而选择先显示、新旧连线混合、节点数量失配和半成品被玩家看到。

## 10. 0.14网页兼容策略

当前网页运行时不能稳定加载原生`node_type=choice`。0.14保留业务上的独立选择身份，但在路线投影层使用兼容载体：

```text
剧情卡：node_type=video
       metadata.logical_node_type=episode
       interaction.has_interaction=false

选择卡：node_type=video
       metadata.logical_node_type=choice
       metadata.choice_ref=choice-xxx
       interaction.has_interaction=true
```

剧情卡用一条`default`边连接唯一选择卡，选择卡再用`choice`边连接目标剧情。选择卡必须保留非空`content.script.text`和`interaction.after_plot_beat`，使网页先呈现决定发生前的剧情，再展示问题和选项。

数组第一项、`entry_node_ref`和唯一入度为0的节点必须同时是有非空完整剧本的`episode-001`剧情卡。路线内全部可视卡统一取得连续且不可二次改写的`episode_ref`；前端不得从选择目标重新编号。

这一兼容层只改变网页承载方式，不改变情绪脊、业务节点身份、十一字段、选择内容、剧本或结局。
